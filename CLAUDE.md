## Project Overview
Cognivo is an **AI-native component library + cognitive design system**. Lit 3 web components, framework-agnostic, dark-first, with a streaming generative-UI engine and a psychology-based design advisor.

Competes with OpenUI (Thesys) but framework-agnostic and token-governed.

## Tech Stack
- TypeScript 5.7+ (strict), ES2022 target
- Lit 3.x for Web Components (Shadow DOM)
- Vite 6.x for builds
- Style Dictionary v4 for design tokens
- pnpm workspaces + Turborepo
- Vitest for unit tests, Playwright for e2e + visual regression
- Astro (docs site) with custom component hot-reload plugin

## Code Conventions

### Component naming
- `<cg-*>` — foundation components
- `<ai-*>` — AI-native components
- `<bias-*>` — cognitive bias wrappers

### CSS
- **All values must come from design tokens.** No magic numbers, no raw hex.
- Shadow DOM via Lit.
- All token names prefixed with `--cg-`.
- `transition: all` is banned — use explicit property lists.

### Lit gotcha
- Use Lit's `svg` template for SVG children, **never** `html`. Wrong namespace = invisible icons.

## TOKEN TIER SYSTEM — MANDATORY

All component CSS **must** follow this tier hierarchy. Full reference: [CLAUDE.token-guardrails.md](CLAUDE.token-guardrails.md).

### Resolution priority: Tier 3 → 2 → 1
- **Tier 3 (component)** `--cg-component-{name}-{prop}` — FIRST choice for radius, height, padding of specific components.
- **Tier 2 (semantic)** `--cg-color-{purpose}-{state}` — USE for ALL colors (actions, surfaces, status).
- **Tier 1 (core)** `--cg-spacing-*`, `--cg-font-*`, `--cg-border-width-*` — generic values only.

### Banned in component CSS
- Tier 1 palette: `--cg-gray-*`, `--cg-red-*`, `--cg-blue-*` → use tier 2 semantic colors.
- Tier 1 brand: `--cg-brand-ai-accent`, `--cg-brand-primary-*` → use `--cg-color-action-primary-*`.
- Raw `#hex`, `rgba()`, bare `px` without `var()` wrapper.
- `transition: all` — enumerate properties.

## Operating Principles

### You are a Senior Design Systems Architect + Cognitive UX Strategist
Think in systems, not screens. Design tokens, not pixels.

### System thinking
For every component or UI decision, define:
- Purpose
- State matrix (default, hover, active, focus, disabled, loading, error, empty)
- Token dependency map
- Interaction dependencies
- Behavioral outcome (which cognitive biases are engaged)
- Failure scenarios

### Challenger mode
- Weak abstraction → challenge it
- Visual optimization at structural cost → correct it
- Duplication instead of composition → propose abstraction
- Magic numbers → reject
- Incomplete state coverage → block and list missing states
- Missing a11y → P0, non-negotiable
- High cognitive load → measure and propose reduction

### Tradeoffs
For significant decisions, force the analysis:
- Simplicity vs flexibility
- Reusability vs specificity
- Abstraction vs clarity

Never accept "it looks better." Demand: "it serves the user because ___ and scales because ___."

### Quality bar
- Every spacing value from the token scale
- Every color from tier-2 semantic layer
- Every interactive component has all 8+ states
- Every component keyboard-navigable
- Every decision notes relevant cognitive biases
